All of your community's endpoints live under `https://<your-community>/api/…`
and answer with JSON.

## Authentication

There are **no API keys**. Authentication goes through an **HttpOnly session
cookie** that is set when you sign in:

- The cookie is `HttpOnly`, `Secure` and `SameSite` — JavaScript cannot reach
  it, and it doesn't travel to other sites unintentionally.
- Requests from the browser have to send it along (`credentials: 'include'`
  with `fetch`, unless they are same-origin anyway).
- Server-to-server access for third-party systems does not currently exist.

Without a valid session, protected routes answer with `401`; without sufficient
permissions, with `403`.

## Error format

Errors below `/api/` come back in a **stable envelope** — designed so you can
program against fixed codes instead of guessing from HTTP status:

```json
{ "ok": false, "code": "VALIDATION_ERROR", "message": "targetId and targetType are required" }
```

| Code | HTTP | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 400, 422 | Input incomplete or invalid |
| `UNAUTHORIZED` | 401 | No (valid) session |
| `FORBIDDEN` | 403 | Signed in, but not permitted |
| `NOT_FOUND` | 404 | Doesn't exist — or isn't visible to you |
| `CONFLICT` | 409 | State doesn't fit (e.g. address already taken) |
| `RATE_LIMITED` | 429 | Too many requests |
| `INTERNAL_ERROR` | 500 and above | Server error |

From `500` upwards the `message` is deliberately generic: internal details,
stack traces and database messages do not leave the server.

::note
`404` also appears when something exists but doesn't belong to your community.
That is deliberate — the answer should not give away that the row exists
elsewhere.
::

## Rate limits

Counting is per IP in a window of one minute:

| Area | Limit per minute |
|---|---|
| Sign-in, code and password reset | 5 |
| Reading comments (`GET /api/comments`, `GET /api/comments/count`) | 120 |
| Writing (comment, post, vote, report) | 60 |
| Guest comments | 5 |

Once the limit is reached, `429` comes back with `code: "RATE_LIMITED"`. For
sign-in and code checks only **failed** attempts count — a successful login
does not use up the budget.

## Cross-origin

Only one endpoint is deliberately callable from other sites:

```
GET /api/comments/count?targetId=<id>&targetType=<type>
→ { "count": 12 }
```

It answers with `Access-Control-Allow-Origin: *`, is **read-only**, works
without cookies and contains no personal data. That is exactly the endpoint
`embed.js` uses for `data-pukalani-count` (see
[Embed widget](/entwickler/embed-widget)).

All other endpoints are **same-origin**. Displaying comments on someone else's
page therefore goes through the iframe widget, not through `fetch` calls of
your own.

## Reading comments (same-origin)

```
GET /api/comments?targetId=<id>&targetType=<type>&sort=new&page=1
```

| Parameter | Required | Values |
|---|---|---|
| `targetId` | yes | Key of the thread |
| `targetType` | yes | Namespace, e.g. `blog` |
| `sort` | no | `new` (default), `top`, `trending`, `discussed` |
| `page` | no | Page number from 1 |

Pagination works over **top-level threads**; each is delivered with its
complete reply tree, so that no reply arrives without the post it answers.
Hidden comments are absent; those deleted by their author remain as
placeholders so the thread stays readable.

## Checking availability

```
GET /api/health
→ { "ok": true, "user": null, "build": "<commit>" }
```

Also answers `HEAD` — uptime monitors and load balancers often check that way.

## Real time

New and changed comments reach open browsers through a WebSocket that the front
end sets up and authenticates itself. There is no public, documented real-time
interface for third-party systems — but in the embedded widget, real-time
updating is included without you doing anything.
